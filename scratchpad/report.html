What was judged worth keeping

Two things, and they are the two the plan is actually missed for.

The invariants where a mistake is silent. Seven, each located in code and stated with its file. Three of them destroy work rather than costing a re-run, and the repo names its own three — the prompt’s guesses were wrong on two of the three, which is itself worth knowing:

  • A step with no commit= wipes its worktree. Journal._ending (sdk/_engine/journal.py:270) ends every step by committing everything or calling Workspace.restore — reset --hard then clean -ffd. Nothing checks the pairing. The only two steps that omit commit= are fix’s reviewer and split’s planner, and both roles declare NO_FILE_WRITES. Not steps.py, where it was expected to be.
  • A landing must be handed back to the parent’s chain. Integration._concluded (sdk/_engine/integration.py:158). Skip journal.advance(head) and the parent believes it is where its last step ended; the next fingerprint miss resets past every landing at once.
  • A red build gate discards a hand-resolved conflict. Integration._gated (sdk/_engine/integration.py:168). Text a person typed into a merge lives in no git object and on no entry. A known cost, pinned by tests/sdk/test_integrate_acceptance.py.

Operator verbs that also destroy data — clear -f, worktree teardown — are not among the three. The criterion is an author mistake that silently deletes paid-for work, not a deliberate destructive command. A sweep for rmtree, unlink, --force, reset, clean and prune found no fourth.

The list of things deliberately not built — twelve, each with one line of reasoning, recovered from the code and the stripped corpus rather than from the plan. No RunStatus; no presentation/ layer; no config-level model override; no CLI positionals; @workflow takes version and nothing else; no fan-out or parallelism helper (zero hits for gather/TaskGroup/parallel under sdk/ — real concurrency is more worktrees); no general subprocess helper; no Integrator.revert(); Store has six members and no more; no retry cleverness on the build gate; no auto() on any enum; no lock in adapters/filesystem/.

The round trip is type-stable, and structurally so

Measured live and after interrupt_after=1 + resume, with a payload carrying tuple, list, nested dataclasses, int, float, bool and str | None: replay is byte-identical to live. Nothing degrades — because the dataclass never crosses the store. The raw JSON is what is persisted, and ReportingTool.read reconstructs identically on both paths. tuple is re-made, float is re-made. This is not luck.

Where it stops being obvious

Four places, in descending order of how badly a reader is stranded.

The payload does not travel through any return value

sdk/_engine/steps.py:87. From Steps.step the value appears out of an AgentOutcome that does not contain it. From AgentRunner.run’s signature there is no payload at all. You must hold three files open — steps.py, ports/agent.py, and whichever adapter — to see the mutable cell. Steps._activity is a second, undocumented instance of the same trick.

A payload class’s identity travels only inside its schema’s title

sdk/tools.py:125 writes "title": f"{kind.__module__}.{kind.__qualname__}". Measured: two dataclasses with identical field names, types and descriptions produce different digests only because of that key — strip title from both and the digests are equal. So the payload type is a fingerprint term, and nothing at either end says so. A reader asking “would two payload types replay each other?” has to guess.

A role that declares no reporting tool returns None typed as its payload

sdk/_engine/steps.py:100. Role[Findings] with an empty tools passes mypy --strict clean and hands the workflow None. The wrong-payload case is caught statically; the missing-payload case is not, because an empty sequence binds P to anything. The ledger stores null, so a resume replays it and fails at the same line.

Two setdefaults that steer a branch inside a third-party function

claude_code/_tools.py:147 adds "type" and "properties" if absent. The reason is in the vendor package: without both, the SDK re-reads the whole dict as a {name: python-type} shorthand and produces a schema nobody could call. You must open claude_agent_sdk to understand two lines of AGL.

Two smaller ones worth recording. The instructions an agent reads (_composed) and the instructions that are fingerprinted (role.instructions) are different strings, so upgrading AGL can change the prompt without changing any digest. And canonical_json does double duty as fingerprint canonicaliser and prompt renderer, so the journal’s reserved __agl_type__ key is rendered into the prompt and read by the model.

A gap in the version-bump story, reproduced

An edit to a payload dataclass’s __post_init__ reaches no fingerprint term. It does not re-run, and it is not silent: on resume it raises InternalError from sdk/tools.py:63. The error text says “sdk/tools.py records why it may not have” — and sdk/tools.py now records nothing. The message is also _refusal(), text written for a model (“Fix all of these and call it again”), surfaced to a person who cannot.

04

Two questions about tools

Whether the reporting tool earns a second concept, and whether a mid-run question can be an ordinary one.

Does the reporting tool earn its keep?

The capability is load-bearing. The second class is not — except for one static check that is real.

Exactly one thing distinguishes a reporting tool at runtime: its payload is the only value a tool call can put on the journal. This was tested rather than assumed. A workflow that captures a payload in its own closure from an ordinary tool’s handler works on a fresh run and breaks on resume — the capture runs inside worker(), which a replayed step never calls. Everything else the reporting tool does (deriving the schema, validating and rejecting in-session, supplying the handler, once-only, turning silence into RoleIncompleteError) an author could write by hand.

One concept would do at runtime: Tool gains an optional payload: type[P] | None and an optional handler. No handler → the framework captures and the payload becomes the step result. That is strictly more expressive than today, because you currently cannot get a derived schema for a tool you also want to handle yourself — which is exactly what the next question needs.

What breaks is Role[P]’s type parameter. Today tools: Sequence[Tool | ReportingTool[P]] binds P from the one member that carries it, and mypy --strict rejects a Role[Findings] declared with a ReportingTool[Other]. Verified: it fires. Under one parametrised class the element type cannot single out the reporting one, and that check is lost. Recovering it needs a second static spelling — which is the present design with extra steps. That is the honest reason two classes exist, and it is a mechanism, not a preference.

Arity, measured: never called → RoleIncompleteError, exit code 6, no entry written — but if commit= was passed the work is committed anyway. Called twice → first wins, second gets a rejection. Bad payload then good → the good one lands, one entry.

Can a mid-run question be an ordinary tool?

Yes — it works, and it costs one thing that matters: the failure mode inverts.

Three of the four expected breakages do not happen. Built and run against both fakes as a throwaway probe (no repo change), a workflow-supplied Tool whose handler calls run.terminal.show works end to end, with no framework change and no layering violation.

The real cost

A question that cannot be answered is fatal today and silent as a tool. Asking captures the handler’s exception, the session loop breaks at the next message, and it is re-raised into the framework. An ordinary tool handler’s exception is absorbed everywhere — by the vendor SDK on one side, by _tools.py:189 on the other, and by both fakes. The model reads “ask failed” and carries on with its own judgement.

Measured side by side: on_question with a raising handler → run() raises, ledger empty. The same handler as a tool → run() returns normally, step recorded. That is the approval gate silently absent and the step reporting a result anyway — which is the exact outcome preflight.py was written to warn about.

So the fold is real but not free. It needs one new mechanism: a way for a tool handler’s exception to abort the session — a ToolResult variant or a sentinel the adapters re-raise. Two adapters and two fakes. Not optional.

Replay survives either way. A question is recorded nowhere — Entry holds fingerprint, value, head and time. A replayed step never asks, because the agent never runs; a step that misses re-asks with no memory. One difference: on_question is not a fingerprint term, but a tool is, so adding an asking tool would change that step’s digest. Arguably more correct — the agent was offered a different tool set — but it is a behaviour change.

06

The two conventions

To be applied later, not now. Both derived from a scan of all 1,500 removed entries and 14,625 named things.

Where the prose actually went wrong

The failure mode is not the one usually assumed. Restating the signature is not a genre here — of 98 single-line function docstrings, only 11 repeat every content word of their own name, and all 11 still add a fact. This codebase never had that problem.

The dominant failure is citation into a document that could be deleted: 518 entries, 35% of the corpus, cite a §, a stage number, a UF marker or a docs/ path. It is worst where prose was densest — 82% of module docstrings carry a dead anchor, against 23% of inline comments.

The repo already found the answer and only half-applied it

.importlinter:164 and scripts/check:445 both say it out loud: “Named, not numbered: gates get inserted, and the numbers move.” Those two files have zero dangling section references between them. tests/, which did not adopt the rule, has 1,434.

The second genre is prose written in the future tense about a plan that changed. The clearest instance: cli/exit_codes.py:45 promised “split is written that way and tickets will be”. workflows/tickets/ never existed — and tests/test_measurable_targets.py:1577 is literally def test_target_twelve_is_unverifiable_because_tickets_does_not_exist(). A test recorded the death of that workflow while a 100-line docstring still promised its future.

Length is bimodal and one tail carries everything: 116 entries over 40 lines are 7.7% of entries but 52% of all removed prose. The median inline comment is 3 lines. A ceiling does not squeeze the ordinary case at all.

Comment convention

The test: if it can be figured out by looking at the code for thirty seconds, it does not get a comment. What survives is what a reader cannot derive — non-obvious usage requirements, what a thing does in one line, the meaning of an input or output where it is not evident.

C1

Say what the code cannot say. Never restate it.

A comment earns its place only by carrying a fact from outside the file: vendor behaviour, an OS or protocol guarantee, a measured number, a units or lifetime fact the type does not encode.

C2

Module docstring: one line. Two at the outside.

C3

Class docstring: one line, shaped “what this is: its parts.” A second paragraph only for a usage requirement a caller must obey.

C4

Function docstring: one line, and only when the signature does not already say it.

C5

Attribute docstring: one line, and only where the field’s type under-describes it. Say what the value means to a reader.

C6

Inline #: for the line beneath it, at most four lines.

C7

Ceiling: 10 lines for any comment, 2 for a module docstring. Anything longer is one of three things, and each has a home — a requirement becomes a test; an architectural rule becomes an ARCHITECTURE.md section or an .importlinter contract; a design narrative goes to documentation outside src/. Workflows never get large explanatory comments.

C8

Named, not numbered. Cite nothing that can be deleted without breaking a build — no §3.6, no 19.2, no UF2.2, no docs/*.md.

C9

Record the outcome, not the history, and never the future. Git holds the history.

C10

State no fact you cannot check, in a place that cannot check it. If a sentence is load-bearing it belongs in a test, an assertion or a type. A comment may summarise the guard and name it; it may not be the guard.

What should have survived

  • adapters/git/_runner.py:149 — “git installs handlers that unlink its own *.lock files on a fatal signal, so SIGTERM plus a moment is the difference between a repository the next command can use and one holding a stale index.lock.” Nothing in the code says why the constant is not zero.
  • adapters/filesystem/store.py:345 — “dir= is load-bearing … os.replace is atomic within one filesystem and raises EXDEV across two.” Delete dir= in a cleanup and atomicity breaks on some machines and not others.
  • adapters/claude_code/translate.py:355 — “Monitor is here because the PowerShell tool’s own refusal message says ‘Monitor runs bash’ — nothing in the permission reference mentions it.” An undocumented vendor fact found by observation; it will not survive re-derivation.
  • scripts/check:76 — “Parallel arrays: bash 3.2 (the system bash on macOS) has no associative arrays.” One line, an external fact, explaining an otherwise-odd data structure. The model comment for the whole repo.

What should not have

  • api.py:1–440 — a 440-line module docstring above 233 lines of code, 1.9× the length of its own module, opening with an argument with a deleted document about code that no longer exists, and containing a sentence in which the comment amends itself in public.
  • sdk/workflow.py:440 — 47 lines of design argument on one private attribute. Its first sentence is a perfect attribute docstring; the other 46 are C7’s third case.
  • api.py:536 — a 24-line inline comment that quotes a deleted document twice and narrates a deliverable number.

The three load-bearing cases

These resolve differently, and together they are the argument for C10.

  • store.py’s global-lock prophecy — recovered, and correctly. The prose said “Nothing below the suite can catch its return, so this paragraph is what guards it.” Someone then wrote tests/adapters/test_filesystem_no_lock.py, which parses the source and refuses a closed set of primitives. Its own docstring opens “store.py predicts this file.” That is exactly what C10 asks for: a comment saying “nothing below can catch this” is a specification for a test. The residual exposure — a bespoke scheme under another name — was covered only by the paragraph, and is now unguarded.
  • _tools.py’s named cost — recorded three times over. In code (the session loop breaks at the next message), in a test asserting identity and ask-count, and in a test comment that reuses the original phrase. The fake does diverge from the real adapter, and the test names the divergence rather than hiding it. Not drift.
  • api.py’s invariant — half-recorded. This is the hole. The behavioural half is pinned by identity, and pinned well. The structural half — “there is no except in this file, and there never may be” — is now written nowhere. An except added tomorrow inside resume, or one that re-raises the same object, passes the existing test.

Naming

Four things are already uniform and need only writing down: 272 of 272 module constants are SCREAMING_SNAKE, 270 annotated Final; 149 of 149 classes are CamelCase; all 23 type aliases likewise; and abbreviation discipline is strong — exactly one single-letter name in all of src/.

The apparent inconsistency is real signal, not noise

The past-participle-versus-verb split tracks something. The cleanest evidence is a pair that splits perfectly: _check_* — 4 functions, all -> None, all raise. _checked_* — 8 functions, all return a value. Twelve functions, zero exceptions. Across all 247 private helpers, 87% of participle-named ones are transformations. The convention should keep the grammar and treat the nine violations as bugs — _written, _emptied, _removed, _drained, _signalled, _stopped, _served, _claimed, _held, every one of which returns None and performs an action.

Test names are similarly consistent and were nearly mis-diagnosed: 81% begin with a determiner, median 11 words, 90% are eight words or longer, none is three words or shorter. The remaining 19% are the same shape with a noun or gerund subject. The test_<what>_<condition> pattern is not in use anywhere.

Module underscores mean two different things, consistently within each half: in adapters/, 16 of 16 underscored modules are package-private with zero leaks; in sdk/_engine/, 7 of 7 leak by design — services alone is imported by four top-level packages. Both rules are defensible; using one mark for both without saying so is not, and the one line that said so was inside src/.

British spelling is settled in prose (behaviour 99 / behavior 0; recognise 39 / recognize 0). The one apparent clash is not one: _initialize mirrors the MCP wire method dispatched three lines above it.

Naming convention

N1

Grammar states the contract. _verb() -> None is an action; _participle() -> X is a transformation; _noun() -> X is a derivation; _sentence_fragment() -> str builds a message.

A past participle must never name a function that returns None.

N2

_check_x raises; _checked_x returns.

N3

A leading underscore on a module means “not on the surface this package promises” — and the package must say which surface.

N4

British English in prose and in AGL’s own identifiers. Where a vendor or protocol spells it American, mirror the vendor exactly and never translate.

N5

One name per concept, and never one name for two. A type defined in ports/ may not be redefined anywhere else.

N6

Parallel siblings share names deliberately. Two adapters implementing one port should use the same internal names — that is not duplication.

N7

Spell words out. Domain-standard short forms are fine (ref, sha, repo, json, http). No single-letter names outside a comprehension.

N8

Test names are sentences — subject, verb, object, 8–14 words, reading as a claim that is true when the test passes.

N9

Constants SCREAMING_SNAKE + Final; classes and type aliases CamelCase; private of either takes one leading underscore.

How each is checked. N9 and most of N7 come free by adding "N" to [tool.ruff.lint] select (currently ["E","F","I","UP","B"]) — not "D", which mandates docstrings that C4 and C5 deliberately do not want. N1, N2, N5 and N8 are AST tests, and the repo already has five tests of exactly that shape. N3’s adapter half is an .importlinter contract; its _engine half cannot be, and must be stated. N4 and N6 are reviewer judgement, with a stated procedure.

Renames worth making — a list, not a change

  1. Answer → RpcAnswer in adapters/openai/_http.py:12. It collides with ports.questions.Answer, and both are in scope in the same package — one module imports each. 4 sites. Cheapest high-value fix in the list.
  2. _wrong → _note_wrong in sdk/tools.py:226. Two other _wrongs are -> InputError factories; this one returns None and appends to a list. The name says “make an error”; the behaviour is “record one”.
  3. _written → _write in adapters/git/_working.py:67, and the eight other N1 violations. Worst of the nine because _write already exists elsewhere as the correct spelling.
  4. Cosmetic: the lone w in workflows/split/__init__.py:31; Entry in rich_terminal/queues.py → Queued; and worktree(name=) → worktree(namespace=), which is last because the nominal call-site count is high and the real ambiguity is low.

Reading this codebase cold

What I would tell someone handed it today, with none of its prose.

The structure is better than the prose was. Stripping 22,666 lines of explanation broke one test, and that test was measuring a sentence.

That is the headline, and it should be reassuring rather than damning. A codebase where two-thirds of the lines are commentary usually has the commentary load-bearing — remove it and things fall over, or nobody can navigate. Here, the layering is enforced by six machine-checked contracts, the ports are small, the fakes are held to the same contract suites as the real implementations, and the test suite asserts behaviour. The prose was a parallel artifact, not scaffolding. It was also, by volume, the least reliable thing in the repo — 35% of it cited a document that could be deleted, and then was.

The architecture is genuinely legible from the tree alone. Eight layers, one arrow, one composition root. Ten minutes with .importlinter and ARCHITECTURE.md and you can place any new file correctly. That is rare and it survived the strip completely, because it was never in the comments — it was in the contracts.

What you cannot see is the ledger. Every hard thing in this system is one idea: a step is a fingerprint, a value and a head, and resume re-runs the workflow from line one, short-circuiting only at recorded fingerprints. Once you hold that, the invariants stop being a list and become consequences — why a workflow may branch only on step results, why canonicalisation must be order-stable, why effects must land inside the workspace, why version must be bumped. Read sdk/_engine/journal.py first. Not api.py, not the workflows. Everything else is arrangement around that file.

The one thing that will actually catch you is that a fingerprint miss is not an error. It is the definition of a new step. There is no assertion divergence can fail and no exception it can raise — the run simply re-does paid-for work, or, where an off-branch digest happens to match, hands back a result for a call that never produced it. Everything else in AGL fails loudly. This one does not, and it is the reason three of the seven invariants exist.

Two habits are worth copying. The first is the structural test: five files in tests/ parse source and assert on its shape rather than its behaviour — no lock in the filesystem adapter, --end-of-options on every git call. That is the right home for a rule a comment can only assert. The second is fakes held to contract suites, which is why the fakes are trustworthy enough that four investigations this session ran real experiments against them in seconds.

Two habits are not. The framework passes a step’s payload back by mutating a cell it installed into an object it handed away — invisible from either end of the call. And the same word means two things in two places often enough that it is worth a rule: Answer, Entry, and conflicted, the last of which fabricates a merge conflict to report a build failure.

The most valuable thing lost with the prose was not explanation. It was the handful of external facts nobody can re-derive: that git unlinks its own lock files on SIGTERM; that os.replace needs dir= to stay atomic; that the Claude SDK reinterprets a schema without both type and properties; that a vendor tool’s refusal message named a tool the permission reference does not. Four facts, roughly, worth about twelve lines. They are in scratchpad/stripped-comments.md and should come back under C1. Almost everything else in those 22,666 lines was the build explaining itself to itself.
